## 경과

revision 1 로 한 번 검증했을 때 24개 중 11개가 `BLOCKED` 였다. 원인은 제품이 아니라 관측 채널
두 가지였다. (1) 숨은 탭에서 브라우저가 `setInterval` 을 1000ms 로 늦춰 700ms 를 잴 수 없었다.
(2) 확장의 신뢰 입력(OS 마우스·키) 경로가 창 상태에 좌우돼 조용히 죽었다 — 도구는 "Clicked" 를
보고하는데 페이지에는 이벤트가 오지 않았다.

무인 복구를 실측으로 확인했다: `select_browser` 재부착 → 새 탭 생성 → 새 `navigate` 전부 해도
`visibilityState` 는 `hidden`, 신뢰 키·클릭 0건이었다. 확장에는 탭 활성화·창 포커스 수단이 없다.

그래서 revision 2 로 SPEC 을 고쳤다. 요지 셋.

1. 낙하 타이밍 주장을 셋으로 쪼갰다 — 상수(6-9c) · 한 tick 당 한 칸(6-9) · 평균 간격 하한 630ms(6-9b).
   억제는 간격을 **늘리기만** 하고 타이머가 겹치면 줄어들므로, 하한 조건은 억제에 면역이면서
   중복 타이머는 그대로 잡는다.
2. 입력 조건의 필수 관측 수단을 합성 디스패치 + 도달성 프로브(`elementFromPoint`)로 정했다.
   OS 입력이 페이지에 닿는지는 제품 속성이 아니라 하네스 속성이라 완료 조건에서 뺐고,
   §6.1 선택 관측으로 내렸다.
3. 그러려면 필요한 공개 API 를 추가했다 — `TetrisApp.tick()` · `TetrisApp.getDropStats()`.

### §6.1 선택 관측 — 건너뜀

`document.visibilityState` 가 끝까지 `hidden` 이었고 카나리아(실제 키·클릭)가 도달하지 않았다.
규정대로 판정에 넣지 않았다. 신뢰 입력 관측은 사람이 Chrome 창을 앞으로 올린 실행에서 가능하다.

### §8 수동 검증

배경 탭이라 사람 눈 확인은 하지 못했다. 통과 판정에 들어가는 항목은 아니다.
창을 올려 `시작` 을 눌러보면 세 항목(부드러운 낙하 · 조작감 · `I→O→T→S` 순환)을 확인할 수 있다.

## 검증 중 부딪힌 함정 (다음 반복이 반복하지 말 것)

1. **강한 억제** — 5분 넘게 숨어 있던 탭은 낙하 타이머가 2450ms 에 **0회**까지 떨어진다.
   6-9b·6-18 은 반드시 페이지를 새로 로드한 직후에 잰다. 새 로드면 1000ms 클램프로 돌아온다.
2. **기준점 오염** — 재시작은 `count` 를 0으로 되돌리지 않는다. 기준 `lastAt` 이 이전 게임 것이면
   평균 간격이 11000ms 처럼 터진다. 현재 게임의 tick 이 한 번 지난 뒤 기준을 잡는다.
3. **폴링 금지** — 숨은 탭은 `setTimeout` 도 1000ms 로 조인다. `sleep(50)`×60 폴링이 실제 60초가 되어
   CDP `Runtime.evaluate` 45초 타임아웃을 냈다. 긴 `sleep` 한 번으로 대체한다.
4. **측정 전 상태 확인** — 측정 도중 블록이 바닥에 닿아 `LANDED` 가 되면 `count` 가 멈춘다.
   측정 창을 열기 전에 `status` 를 확인한다.
