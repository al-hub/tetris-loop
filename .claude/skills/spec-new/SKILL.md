# spec-new — 다음 SPEC 문서 만들기

**문서만 만든다.** 산출물 코드를 쓰지 않는다. 검증하지 않는다.
`/spec-loop` 을 호출하지 않고 `ScheduleWakeup` 도 호출하지 않는다.
루프를 시작하는 것은 사람의 몫이다.

이 스킬의 존재 이유: SPEC_00 은 revision 1 에서 완료 조건 여러 개가 관측 불가였고
자료구조 키 이름이 안 정해져 구현자마다 다르게 읽혔다. rev2 로 개정하며 얻은 규칙을
문서 생산 단계에 게이트로 박아 같은 낭비를 막는다.

프로젝트 제약은 `CLAUDE.md`, 하네스 구조는 `docs/LOOP_HARNESS.md` 에 있다. 시작 전에 읽는다.

## 단계 0 — 선행 조건

`.loop/state/progress.json` 을 읽는다.

| 현재 `status` | 행동 |
|---------------|------|
| `PASSED` | 정상 진행 |
| `HALTED` | 진행 가능. 단 새 SPEC 이 정지 사유를 해소하는지 한 줄로 밝힌다 |
| `PENDING` · `IN_PROGRESS` · `VERIFYING` · `FAILED` · `BLOCKED` | **멈춘다.** 진행 중인 SPEC 을 갈아치우면 반복 이력과 리포트가 끊긴다 |

멈출 때는 현재 SPEC·상태·반복 횟수를 보고하고, 사람이 "현재 SPEC 폐기" 를 명시적으로
말하면 그때만 진행한다. 폐기하는 경우 `.loop/reports/` 는 지우지 않는다.

## 단계 1 — 목표 확정

인자로 받은 목표 한 줄을 출발점으로 삼는다. 인자가 없으면 무엇을 만들지 묻는다.

**SPEC 은 결정이 끝난 문서다.** 문서 안에 `[사람 확인 필요]` 를 남기지 않는다.
그건 구현 단계의 장치이고, 여기서는 미정 항목을 지금 사람에게 물어 없앤다.

물어야 하는 것 (추측 금지):

- 이번 단계의 범위와 **범위 밖**의 경계
- 화면 문구, 라벨, 상태 이름 같은 사용자에게 보이는 문자열
- 자료구조의 키 이름과 값
- 레이아웃 수치, 브레이크포인트, 타이머 간격 같은 상수

선택지가 두세 개로 좁혀지면 `AskUserQuestion` 으로 고르게 한다.
질문은 서로 독립적인 것만 한 번에 묶는다.

## 단계 2 — 번호와 파일명

```bash
ls SPEC_*.md
```

기존 최대 번호 + 1, 두 자리 zero pad. 파일명은 `SPEC_NN_<SLUG>.md`,
`<SLUG>` 는 영문 대문자 스네이크 (예: `SPEC_01_FALLING_PIECE.md`).

frontmatter:

```yaml
---
id: SPEC_NN
title: <한국어 한 줄>
revision: 1
depends_on: [SPEC_00]
max_iterations: 3
---
```

`depends_on` 은 앞 SPEC 의 산출물에 실제로 의존할 때만 적는다.
`max_iterations` 기본값은 3 이고, 사람이 다른 값을 말하지 않으면 바꾸지 않는다.

## 단계 3 — 문서 작성

`SPEC_00_PROJECT.md` 와 같은 절 구성을 따른다. 절을 임의로 빼지 않는다.

| 절 | 담을 것 | 주의 |
|----|---------|------|
| §1 목표 | 이번 단계가 끝났을 때 무엇이 되는지 | 두세 문장. 구현 방법을 쓰지 않는다 |
| §2 기술과 파일 구조 | 앞 SPEC 과 **달라지는 것만** | 같으면 "SPEC_00 §2 와 같다" 로 끝낸다. 산출물 파일이 늘면 `CLAUDE.md` §2 도 §6 배선에서 함께 고친다 |
| §3 화면 정의 | DOM 계약 (`data-role`), 문구, 레이아웃 | 문구는 원문 그대로 코드 블록에 넣는다 |
| §4 상태와 공개 함수 | 공개 API 이름·인자·반환, 자료구조 키와 값 | 키 이름과 값 타입을 고정한다. "적절한 객체" 같은 표현 금지 |
| §5 범위 밖 | 이번에 **만들지 않는** 것 | 다음 SPEC 이 할 일을 여기 적는다 |
| §6 완료 조건 | 번호 붙은 체크박스 목록 | 단계 4 감사를 전부 통과해야 한다 |
| §7 자동 검증 | 러너 출력 형식, 필수 테스트 `data-name` 표 | 개수와 이름을 고정한다 |
| §8 수동 검증 | 자동으로 관측 못 하는 것만 | 시각 판단 항목만 남긴다 |
| §9 안전과 정지 조건 | 폴더 밖 금지, 반복 예산 | `max_iterations` 와 같은 값임을 명시 |
| §10 다음 단계로 넘기는 것 | 의도적으로 남긴 것과 이유 | §5 와 짝이 맞아야 한다 |
| §11 해석 고정 근거 | 갈릴 수 있던 지점과 정한 쪽, 이유 | 단계 1 에서 사람에게 물어 정한 것을 여기 적는다 |

완료 조건 번호는 `§번호-순번` 형식으로 쓴다 (`6-1`, `6-2`, …).
`progress.json` 의 체크리스트 키와 `spec-verify` 관측표가 이 번호를 참조한다.

## 단계 4 — 자기 감사

작성한 문서를 아래 게이트에 하나씩 걸어 본다. **하나라도 걸리면 문서를 고친다.**
고치지 못하는 항목은 사람에게 물어 결정을 받는다.

1. **관측 도구 지정** — 완료 조건마다 "무엇으로 관측하나" 에 답이 있어야 한다.
   허용되는 관측 수단은 이것뿐이다:
   파일시스템(`ls`·`grep`) · DOM 개수 · DOM 텍스트 비교 · 콘솔 메시지 ·
   뷰포트 리사이즈 후 측정 · 키 입력·클릭 후 스냅샷 비교 · 콘솔에서 공개 함수 호출.
   여기에 안 걸리는 조건은 완료 조건이 될 수 없다.
2. **부재 증명 금지** — "…이 없어야 한다" 로 끝나는 조건은 관측 범위를 붙여 유한하게 만든다.
   (나쁨: "콘솔 오류가 없다" / 좋음: "로드 완료 후 5초까지 error 레벨 0건, warning 은 세지 않는다")
3. **자료구조 고정** — 반환 객체의 키 이름, 값 타입, 동결 여부가 문서에 있어야 한다.
   테스트가 비교할 대상이 없으면 §7 을 쓸 수 없다.
4. **문자열은 문자 단위** — 화면 문구를 완료 조건이 검사한다면 "문자 단위로 일치" 라고 쓰고
   원문을 코드 블록에 그대로 넣는다. "의미만 맞으면" 은 판정을 사람 주관으로 되돌린다.
5. **수치 유한 열거** — 연속 구간을 검사 대상으로 두지 않는다.
   브레이크포인트는 숫자로, 검사할 값은 목록으로 적는다.
6. **테스트 이름 고정** — §7 에 필수 `data-name` 표와 최소 개수가 있어야 한다.
   "모든 테스트 통과" 는 테스트 한 개만 써도 충족되는 자기 채점이다.
7. **하네스 파일 예외** — 파일 집합을 검사하는 조건을 쓴다면
   `CLAUDE.md` · `MEMORY.md` · `SPEC_*.md` · `docs/` · `.claude/` · `.loop/` · `.git/` · `.gitignore`
   를 세지 않는다고 명시한다. 빼먹으면 영구 실패 조건이 된다.
8. **`file://` 전용 관측 금지** — 브라우저 확장이 `file://` 스킴을 거부한다
   (`Can't interact with browser-internal or unparseable URLs`).
   검증은 로컬 정적 서버(`http://localhost`) 경유로만 관측할 수 있다.
   §2 가 `file://` 동작을 **요구하는 것은 괜찮지만**, §6 완료 조건에 넣으면 관측 불가가 된다.
9. **`devicePixelRatio` 경계 조건 주의** — 폭 브레이크포인트를 완료 조건에 넣을 때
   경계값 자체(예: 정확히 768px)에서의 배치를 판정 대상으로 삼지 않는다.
   dpr 이 정수가 아니면 실측 CSS 폭이 0.01px 어긋나 판정이 흔들린다.
   경계 아래·위 값(예: 390px 과 1024px)으로 적는다.
10. **§5 와 §6 충돌 없음** — 범위 밖 기능을 완료 조건이 요구하지 않는지 대조한다.
11. **§6 커버리지** — 완료 조건 각 항목이 §7(자동) 또는 §8(수동) 중 어디서 판정되는지
    빠짐없이 정해져 있어야 한다.

감사 결과를 사람에게 표로 보여준다. 통과하지 못한 게이트가 있으면 무엇을 어떻게 고쳤는지 적는다.

## 단계 5 — 사람 승인

배선 전에 멈춘다. 다음을 보여주고 승인을 받는다.

- 파일명과 제목
- §1 목표 (그대로)
- 완료 조건 개수와 목록 한 줄 요약
- §5 범위 밖 목록
- 단계 4 감사 결과

**승인 없이 단계 6 으로 가지 않는다.** 배선은 현재 SPEC 을 바꾸는 되돌리기 번거로운 동작이다.

## 단계 6 — 배선 (승인 후)

완료 조건 목록은 네 군데에 복제되어 있다 (`docs/LOOP_HARNESS.md` §7).
**넷을 한 번에 맞춘다.** 하나라도 빠지면 다음 tick 이 옛 SPEC 을 본다.

### 6a. `.loop/state/progress.json`

- `current_spec` · `spec_file` → 새 SPEC
- `spec_revision` → `1`
- `iteration` → `0`
- `status` → `PENDING`
- `failure_signatures` → `[]`
- `checklist` → 새 완료 조건 키 전부 `"UNKNOWN"`
- `last_report` → `null`
- `human_input_needed` → `null`
- `updated_at` → `date -Iseconds`

체크리스트 키 형식은 `<조건번호>_<snake_slug>` 다 (예: `6-1_file_set_exact`).
쓴 뒤 반드시 파싱 검증한다.

```bash
node -e "JSON.parse(require('fs').readFileSync('.loop/state/progress.json','utf8'));console.log('progress.json OK')"
```

### 6b. `.claude/skills/spec-verify/SKILL.md`

단계 1(정적 검사)·단계 2(브라우저 검사) 표를 새 완료 조건으로 **교체**한다.
항목마다 단계 4 게이트 1 에서 정한 관측 수단을 적는다.
판정 규칙·반환 형식·"관측하지 못한 것을 PASS 로 적지 않는다" 부분은 건드리지 않는다.

이 갱신을 빼먹으면 검증 게이트가 지난 SPEC 을 관측하고 통과를 보고한다. 가장 위험한 누락이다.

### 6c. `CLAUDE.md`

- §1 의 현재 SPEC 파일명
- §2 산출물 파일 목록 — 새 SPEC 이 파일을 늘리거나 줄일 때만
- §3 코드 구조 · §4 범위 통제 — 새 SPEC 이 공개 API 를 늘릴 때만

### 6d. `MEMORY.md`

현재 표 · 체크리스트(전부 `—`) · 반복 기록(빈 상태) · 다음 단계를 새 SPEC 기준으로 갱신한다.
지난 SPEC 의 결과는 **정지 이력**에 한 줄로 남긴다. 진행 상태만 쓰고 설계 설명은 넣지 않는다.

## 단계 7 — 커밋

```bash
git add -A
git commit -m "$(cat <<'MSG'
docs(SPEC_NN): <한 줄 요약>

<이번 SPEC 이 무엇을 요구하는지 2~3줄>
<배선한 파일: progress.json, spec-verify 관측표, CLAUDE.md, MEMORY.md>

Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
MSG
)"
```

문서 커밋과 구현 커밋을 섞지 않는다. 구현은 `spec-loop` 이 통과했을 때만 커밋한다.

## 단계 8 — 보고

다음 명령은 이것이다.
